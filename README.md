# [Alloy Analyzer](https://alloytools.org/) plug-in for IntelliJ-based IDEs

> Available in [JetBrains Marketplace](https://plugins.jetbrains.com/plugin/35343-alloy-analyzer)

The plugin includes the Alloy 6.2.0 analyzer and runs it inside the IDE, on its own Java runtime: no separate process, no system Java installation and no IntelliJ Platform LSP support are needed. It installs in any IntelliJ-based IDE from 2026.2.

- **File type**: `.als` files are recognized as Alloy models and shown with the Alloy icon. Alloy models embedded in Markdown (`.md`) files are not supported.
- **Syntax highlighting**: keywords, temporal operators (including the prime `'`), operators, identifiers, numbers, strings, comments (line, block and documentation), braces, parentheses, brackets, commas and dots, and invalid characters. Every category can be customized in *Settings | Editor | Color Scheme | Alloy*.
- **Editing**: brace matching and auto-closing, line and block comments, folding of bodies, comments and imports, and keyword completion, on any content, including models with errors.
- **Diagnostics**: the analyzer's syntax and type errors and its warnings, at the ranges it reports, for the current text of the file, saved or not. An error in an opened module is also reported at its `open`. Diagnostics appear in the error stripe and the *Problems* tool window.
- **Inspections**: while the model type-checks, weak warnings point out mistakes that the analyzer accepts in silence, in an "Alloy" group of *Settings | Editor | Inspections* where each one can be turned off. A command that scopes some signatures but leaves one used by `var` fields at the default scope; a scope written as an upper bound for a signature that a module parameter such as `util/ordering[Id]` makes exact (an overall `for N` is only shown on Alt+Enter); a `seq` bound smaller than the elements of a `var` field of `seq` type; and an event predicate, one that constrains the next state with `'` or `after`, that leaves some `var` field or `var sig` unconstrained (a missing frame condition). Quick-fixes add the scope, write `exactly`, raise the `seq` bound, or add `f' = f`. A `// noinspection <id>` comment before a paragraph, written by *Suppress for predicate/command*, turns an inspection off for it.
- **Semantic features**: hover and *Quick Documentation* (the declaration as the analyzer explains it, with its `/** ... */` comment), go to declaration (also into the bundled `util/*` library modules, read-only), highlight usages, *Find Usages*, rename, the *Structure* view, breadcrumbs and *Go to Symbol*. When the model type-checks, references resolve exactly as the analyzer resolves them; while it does not, they resolve by name, innermost scope first, so navigation keeps working while editing. *Find Usages* lists the uses found by name in files with errors as unconfirmed, and rename is refused until every affected file type-checks.
- **Running commands**: every `run` and `check` command has a run icon in the gutter that executes it right away. The result appears as an inlay hint at the end of the command's line: running, instance found, no instance found, counterexample found, no counterexample found, stopped before completion, or a failure such as "Model has errors". Hovering the hint shows everything the analyzer reported. The gutter icon of a running command is a spinner, and clicking it opens a menu with *Stop*. Clicking the hint shows an instance or counterexample in the *Alloy Instance* tool window, or stops a running analysis. Editing the file or changing the analyzer settings marks its results as outdated. Progress is shown as a cancellable background task in the status bar. Only one analysis runs at a time in each project.
  - **Expectations**: a command with `expect 1` or `expect 0` is a test. Its hint says whether the outcome is "as expected" or "contrary to expectation", and after a result its gutter icon is the green passed or red failed test icon (red also when its analysis fails, for example in a model with errors). The icon stays when the result becomes outdated, its tooltip then saying "(outdated)", and clicking it runs the command again. Commands without `expect`, and stopped ones, keep the run icon.
  - **Vacuity**: when a `check` finds no counterexample, the same execution goes on to check that it did not pass vacuously. It solves the model's facts within the check's scope, together with the assertion's premise when the assertion is `A implies B`, also under `all` (`some … | A`) or `always` (`eventually A`). If they have no instance, there was nothing for the assertion to be checked against: the check passed vacuously, its hint says "(vacuous)", its gutter icon is the yellow vacuous icon (also with `expect 0`), and its tooltip says whether the facts or the premise have no instance. While this runs, the hint already shows the check's result, followed by "checking vacuity…", and the status-bar task says "Checking vacuity…"; stopping it, or a failure, keeps the check's result and the tooltip says that vacuity was not determined.
- **Commands as tests**: *Run 'All commands in a.als'*, in the context menu of an Alloy file in the editor or in the *Project* view, executes every `run` and `check` command of the file, one after another in source order, in the IDE's test runner. The Run tool window shows one node per command, such as `run show` or `check noCycles`, with the analysis time and the analyzer output. A command fails when its `expect` is not met, when its analysis fails, or when it passes vacuously; otherwise it passes. Double-clicking a node opens its command, *Rerun Failed Tests* executes only the failed commands, and *Stop* stops the command being executed and skips the rest. The *Alloy Commands* run configuration can be saved and run again from the toolbar. Hints and gutter icons are updated as for gutter runs, and the suite holds the project's single analysis until it ends.
- **Alloy Instance tool window** (on the right of the editor): shows one instance or counterexample at a time, with a header naming the file, command and line it came from (clicking it navigates there). Its *Visualization* tab draws the graph with the Alloy visualizer's magic layout; the *Text* and *Table* tabs show it as the analyzer prints it. Its toolbar asks for a new configuration, trace, initial state or fork, which keep the graph's theme and projections, steps through the states of a trace, and projects over any number of signatures.
- **Evaluator**: a panel of the *Alloy Instance* tool window, shown from its toolbar, evaluates Alloy expressions and formulas in the shown solution, as the desktop evaluator does, and at the selected state of a trace, so that `after`, `always`, primes and the other temporal operators are interpreted from there, along the whole trace. Expressions can use every name of the model as it was analyzed (also for an outdated result), those of opened modules, and the solution's atoms (`Node$0`) and skolems (`$show_n`). The field highlights Alloy syntax, completes those names, and keeps a history of evaluated expressions (Up and Down). Sets of tuples show their size and expand to one row per tuple; errors, such as unknown names or higher-order quantification, are shown in place of the value. As in the debugger, expressions can be kept as watches, which can be added, edited, removed and reordered, and are evaluated again whenever another state or a new solution is shown, and are highlighted when their value changes. Watches are kept per model file, in the project's workspace. Evaluations run in the background, so a slow one never blocks the IDE.
- **Analyzer settings**: *Settings | Languages & Frameworks | Alloy* sets the solver, skolem depth, overflow prevention, unsat core minimization and granularity, non-fatal warnings, recording of the Kodkod input/output and partial instance inference for every project, and whether passing checks are checked for vacuity (*Check vacuity of passing checks*, on by default; turning it off saves the time of the extra analysis). The solver list offers the pure-Java SAT4J variants, and the external solvers whose executables are on the `PATH`: Yices (`yices`), Plingeling (`plingeling`), and Electrod with NuSMV or nuXmv (`electrod` with `NuSMV` or `nuXmv`). Solvers that need a native library are not offered, since they could crash the IDE. These settings are independent of the Alloy desktop application's preferences. Applied changes take effect with the next analysis; a running analysis goes on with the settings it started with.

Analyses use the IDE's own memory. An analysis that runs out of memory or stack is reported as a failure, but models with very large scopes are better run in the Alloy desktop application.
