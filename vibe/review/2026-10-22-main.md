# Code review: `src/main/kotlin` (2026-10-22)

**Scope.** All 111 Kotlin files (about 10,300 lines) under `src/main/kotlin/com/serranofp/alloy`, at commit `39d84ac`. Tests, grammar, resources and OpenSpec specifications are out of scope; they were only read for context. Findings were checked against the code (and, for analyzer behaviour, against the Alloy 6.2.0 sources). The two semantic bugs in `simplifications` were reproduced with a temporary test, which was then removed. Findings marked *plausible* are real code paths that were not reproduced.

## Summary

Overall the code is good. It is compact, consistently documented with KDoc that explains *why* (and points to the analyzer code it mirrors), and well layered:

- a flat PSI with stubs;
- the analyzer's `CompModule` as the source of truth for semantics;
- pure, testable cores (`TraceStripLayout`, `DarkColors`, `AlloyCommandBounds`, the rewrite renderer);
- thin platform adapters.

Locking in the run and analysis layers was clearly thought through.

The main weaknesses fall into a few themes that show up in several packages:

1. **Cancellation and threading.** No analyzer parse ever calls `ProgressManager.checkCanceled()`, and the external annotator holds the model computation inside `ReadAction.computeBlocking`. A long parse therefore blocks the next keystroke's write action. The AST walks in inspections and simplifications have no cancellation checks either. In the viewer, solution XML writing, viz layout and trace diffs run on the EDT.
2. **How a command is identified.** `AlloyCommandRef` (label + index) is resolved by label only. Two commands with the same label (such as `check A for 3` / `check A for 6`) run and display the wrong command. Its data-class equality includes the index, so results disappear when commands are inserted above.
3. **Robustness of long-lived state.** If launching throws (including a `ProcessCanceledException`), `AlloyRunService` stays busy until the project is reopened. A stop can be lost during the check→vacuity handover. The viewer leaks every graph pane through one shared `LayerUI`. Results keep every `A4Solution` for the whole session. Stopping an analysis can kill other analyses' external solver processes.
4. **Duplicated work per highlighting pass.** Five simplification inspections each walk the model with their own `AlloySourceText`. `AlloyCommandBounds` is recomputed by four inspections for each command. Resolving each reference rebuilds a `DocumentImpl` of the file and visits the whole module. Several of these could hang off the cached `AlloyModelResult.Model`.
5. **Internationalization.** `messages/AlloyBundle.properties` only has the `plugin.xml` display names, and there is no `AlloyBundle` class. Every message, fix name, action text and settings label is hardcoded, and some strings are repeated (for example `" (outdated)"` in three places).

- ✅ Make the model computation cancellable and single-flight per file. Then hang the derived data (position→target index, `AlloySourceText`, `AlloyRewriteIndex`, per-command bounds) off `AlloyModelResult.Model` instead of static maps or per-call recomputation.

# Findings by package

## Core: semantics, analysis, settings, editor, psi, lexer, parser, highlighting, top-level files

### Overview

This part of the plugin covers the language basics, the semantic layer and the analysis engine:
- **Language basics:** file type, lexer adapter, Grammar-Kit parser definition, stub-based declarations with a name index, highlighting, folding, commenter, brace matching, structure view and breadcrumbs.
- **Semantic layer:** `AlloyModelService` parses and type-checks each file with the bundled `CompUtil` and caches the result. Resolution, documentation, diagnostics, find usages and rename build on it. When the model does not type-check, they fall back to name-based scopes (`AlloyScopes`).
- **Analysis engine:** each analysis runs on its own large-stack thread with cooperative stopping. `StoppableSatFactory` expires SAT4J solvers and kills external solver processes. Analyzer options are app-level settings.

The code is compact, well documented and mostly follows platform conventions. Positions are mapped carefully against the exact text the analyzer saw.

The biggest issue is threading. The analyzer parse runs inside read actions that cannot be cancelled, and in one place inside an explicit blocking read action. Other problems:
- per-reference work grows with the size of the model (a quadratic pattern);
- stopping one analysis can kill another analysis's external solver processes;
- rename crashes when the new name is a keyword;
- several small text-range mistakes in the documentation provider.

### High

- ✅ **The analyzer parse holds a read lock that cannot be cancelled, so typing freezes during long parses** — `src/main/kotlin/com/serranofp/alloy/semantics/AlloyExternalAnnotator.kt:30`, `src/main/kotlin/com/serranofp/alloy/semantics/AlloyModelService.kt:81-93`
  - `doAnnotate` wraps the whole `model(file)` in `ReadAction.computeBlocking`. The `CachedValue` provider runs `CompUtil.parseEverything_fromFile` over the root file and every project module it opens, and nothing in it ever calls `ProgressManager.checkCanceled()`.
  - The platform cancels background read actions when a write action is pending. That only works if the code checks for cancellation, so a keystroke's write action waits on the EDT until the parse and type-check finish.
  - The same applies to every other route into `model()` from a background thread: `AlloyReference.multiResolve`/`exactTarget` through `availableModel`, `AlloyUsageTypeProvider`, the inspections and `filesWithErrors`.
  - **Failure scenario:** a model of a few thousand lines that opens several project modules takes about a second to type-check. Each edit triggers the annotator, and the next keystroke blocks the UI for that long.
  - **Fix:**
    - Make the parse cancellable: in the `A4Reporter` created in `analyze()`, override `parse`/`typecheck` (CompModule calls them for every paragraph) to call `ProgressManager.checkCanceled()`.
    - Run the work in a non-blocking read action (`ReadAction.nonBlocking { … }.executeSynchronously()` or `readAction {}`), not `computeBlocking`.
    - Unwrap the cancellation in `analyze()`, because `CompUtil` wraps every non-`Err` throwable in `ErrorFatal` (`CompUtil.java:390-394`). Rethrow when `e is ErrorFatal && e.cause is ControlFlowException`.
    - Never cache a cancelled computation.
    - Alternatively, copy the texts in a short read action, parse with no lock held, and cache against the files' modification stamps.

### Medium

- ✅ **The `ControlFlowException` branch can never run, and real cancellations would be cached as "Unavailable"** — `src/main/kotlin/com/serranofp/alloy/semantics/AlloyModelService.kt:136-143`
  - `CompUtil.parseEverything_fromFile` catches `Throwable` and rethrows anything that is not an `Err` as `ErrorFatal("Unknown exception occurred", ex)`. A `ProcessCanceledException` coming out of the parse would therefore match `is ErrorFatal`. It would be logged as "The Alloy analyzer failed" and cached as `Unavailable` until the next PSI change.
  - This is harmless today only because nothing in the parse checks for cancellation. It becomes a real bug as soon as the High fix is applied.
  - **Fix:** check `e.cause` (recursively) for `ControlFlowException` before classifying.

- ✅ **Resolving one reference walks the whole model and rebuilds a document of the whole file** — `src/main/kotlin/com/serranofp/alloy/semantics/AlloyReference.kt:58-78`, `:98-109`
  - `exactTarget()` (and its duplicate `exactExplanation()`) builds a `DocumentImpl` from the file's full text on every call, which is O(file size). It then calls `CompModule.find(pos)`, which visits every expression of the module (`visitExpressionsResilient`, `CompModule.java:2647`). `declarationAt` builds a second `DocumentImpl`.
  - `ResolveCache` is cleared on every PSI change. So after each edit, resolving N references costs O(N × model size).
  - The affected features are find usages, rename, the usage-type provider (which calls `isExact()` and resolves again) and model-based inspections.
  - **Fix:** build a position-to-target index once per `AlloyModelResult.Model` (one visit of all expressions), for example lazily inside the model. Also keep line-start tables per file in `AlloyModules` instead of `DocumentImpl`. Merge `exactTarget` and `exactExplanation` into one lookup that returns `(Expr, declaration)`.

- ✅ **Stopping an analysis kills unrelated solver processes** — `src/main/kotlin/com/serranofp/alloy/analysis/StoppableSatFactory.kt:71-81`, `src/main/kotlin/com/serranofp/alloy/analysis/AlloyAnalysisEngine.kt:101`
  - `destroySolverProcesses()` force-kills every descendant of the IDE process that runs one of the factory's executables (`yices`, `plingeling`, `electrod`, …) and started after `started`. It also kills those whose start time is unknown (`orElse(true)`).
  - That set includes processes of other concurrent analyses: another command, another project, or a vacuity follow-up. It also includes processes the user started in the IDE terminal.
  - It gets worse with enumerations. `rearm()` reuses the original analysis's factory, so `started` is the time of the first run, possibly hours earlier.
  - **Failure scenario:** two checks run with Plingeling in two projects. Stopping one kills the other's solver, which then fails with an unexpected exception.
  - **Fix:** keep track of the processes this factory actually started. Diff `ProcessHandle.current().children()` around `original.instance()` inside `createSolver`, or wrap the external solver if pardinus exposes it. Kill only those processes, and reset `started` (or the tracked set) in `rearm()`.

- ✅ **Renaming to an Alloy keyword throws inside the write action** — `src/main/kotlin/com/serranofp/alloy/psi/AlloyNamedDeclaration.kt:18-22`
  - No `lang.namesValidator` is registered in `plugin.xml`, so the platform's `DefaultNamesValidator` applies. It accepts any Java identifier, including `sig`, `run`, `all`, `always`, `this`, `Int`, `String` and `steps`.
  - `AlloyElementFactory.identifier("sig")` parses `sig sig {}`, finds no `SigName` and throws `IllegalArgumentException` from `setName`/`handleElementRename` in the middle of the refactoring. The user sees an IDE error instead of a validation message.
  - On the other side, names with `"` (allowed by the lexer's `IDENTIFIER`) are rejected.
  - **Fix:** add an `AlloyNamesValidator`. `isKeyword` should check the name against `AlloyTokenSets.KEYWORDS`/`TEMPORAL_OPERATORS`. `isIdentifier` should run `AlloyLexer` and require exactly one `IDENTIFIER` token. In the factory, also check that the created identifier's text equals `name`.

- ✅ **References in evaluator fragments and non-physical copies reach the model service without the guards other callers use** — `src/main/kotlin/com/serranofp/alloy/semantics/AlloyReference.kt:48`, `:60`, `:72`
  - Every other model client (`AlloyExternalAnnotator.collectInformation`, `AlloyModelInspection.checkFile`, `AlloyRewriteIntention.find`) first checks `virtualFile != null && !isAlloyEvaluatorFragment`.
  - `multiResolve`, `exactTarget` and `exactExplanation` call `availableModel(file)` before checking `file.virtualFile`. Two consequences:
    - In the evaluator editor, a physical `LightVirtualFile`, any background resolve (for example highlighting the identifier under the caret) parses the expression as a module on every keystroke. The parse always fails.
    - In a non-physical copy, `virtualFile` is null, and `collect()` passes it to `AlloyPositions.filename(file.virtualFile)`, a non-null Kotlin parameter, which throws an NPE. Examples are preview copies used by platform intentions or quick fixes that resolve references.

    Confidence for the NPE path: plausible.
  - **Fix:** check `file.virtualFile != null && !file.isAlloyEvaluatorFragment` before `availableModel`. Make `model()` reject such files explicitly (return `Unavailable`) instead of failing with an NPE.

- ✅ **Documentation signature is cut at the first `)`, `]` or `,` inside a bound** — `src/main/kotlin/com/serranofp/alloy/semantics/AlloyDocumentationProvider.kt:47-61`
  - `paren_group` and `bracket_group` are private rules in `Alloy.bnf`. Their tokens are therefore direct siblings of the field or parameter, and the sibling walk stops at `RPAREN`/`RBRACKET`/`BAR` and at any `COMMA` after the colon, even when the token is nested.
  - **Failure scenarios:**
    - `sig S { f: set (A + B) }` → the doc for `f` shows `f: set (A + B`.
    - `pred p[x: A -> B[y, z]]` → it is cut at `B[y`.
    - `enum E { A, B, C }` → for each member, the doc shows `A, B, C`, because there is no colon so the commas never stop the walk.
    - `let x = a, y = b | …` → for `x`, the doc shows `x = a, y = b`.
  - **Fix:** track nesting depth while walking (only stop on closers and commas at depth 0). For let and enum members, also stop at a comma before any `:`/`=`.

- ✅ **Completion documentation can show the analyzer's explanation of the reference at the caret instead of the selected item's** — `src/main/kotlin/com/serranofp/alloy/semantics/AlloyDocumentationProvider.kt:23`, `:78-82`
  - `explanation(originalElement)` is used whenever the element at the caret has an `AlloyReference`. Nothing checks that this reference resolves to `element`.
  - When docs are shown for a completion lookup item, `element` is the lookup's declaration while `originalElement` is the leaf at the caret.
  - **Failure scenario:** with the caret on an existing reference `foo`, browsing completion items shows `foo`'s explanation for every item (confidence: plausible).
  - **Fix:** use the explanation only if `reference.exactTarget() == declaration`, and otherwise fall back to `source(declaration)`.

### Low

- ✅ **The `Rename` progress can be cancelled, but cancelling is not handled** — `src/main/kotlin/com/serranofp/alloy/semantics/AlloyRename.kt:36-41`
  - `runProcessWithProgressSynchronously(ThrowableComputable, …, canBeCanceled = true, …)` rethrows the `ProcessCanceledException` raised by `ReferencesSearch`/`checkCanceled` to the EDT caller. `substituteElementToRename` does not catch it.
  - On cancel, the rename should be aborted quietly (`return null`), not surface an exception (confidence: plausible).
  - **Fix:** catch `ProcessCanceledException` and return a refusal or null.

- ✅ **The "read-only library module" message also appears for read-only project files** — `src/main/kotlin/com/serranofp/alloy/semantics/AlloyRename.kt:33-34`
  - `!file.isWritable` also covers write-protected project files, so the message is misleading.
  - **Fix:** split the two conditions and give each its own message.

- ✅ **Doc comments are not found for fields that have modifiers, or for later fields in a group** — `src/main/kotlin/com/serranofp/alloy/semantics/AlloyDocumentationProvider.kt:66-70`
  - In `/** Contents */ var contents: set Object`, the field's previous sibling is the `VAR` token, so `skipWhitespacesBackward` does not reach the comment. The same happens with `private`/`disj`, and for `b` in `/** doc */ a, b: A`.
  - **Fix:** walk back over `VAR`/`PRIVATE`/`DISJ`/`COMMA`/`fieldDecl` siblings of the same group, as `AlloyScopes.isPrivate` already does.

- ✅ **By-name scopes treat a binder as out of scope in the bounds of later binders** — `src/main/kotlin/com/serranofp/alloy/semantics/AlloyReference.kt:177-190`
  - A quantifier's or comprehension's binders are only visible from `|` onwards. Alloy, however, allows `all x: A, y: x.next | …`, where `x` in the second bound refers to the first binder.
  - When the model has errors, that `x` resolves by name to a field or top-level `x`, or to nothing. Rename and find usages then go wrong.
  - **Fix:** make each binder visible from the end of its own `binder_group`.

- ✅ **Errors inside library modules are reported for the whole file instead of at the `open`** — `src/main/kotlin/com/serranofp/alloy/semantics/AlloyExternalAnnotator.kt:65-75`
  - `modules.files` excludes library modules (`AlloyModelService.kt:31-33`). For an error whose position is in `/$alloy4$/models/util/*.als`, `opened` is never found, so the error becomes a file-level annotation even though an `open util/…` leads to it.
  - **Fix:** also map library opens, for example through `AlloyModelService.openedModule`, and match `error.pos.filename` against library filenames.

- ✅ **Some module-graph changes do not invalidate the cache** — `src/main/kotlin/com/serranofp/alloy/semantics/AlloyModelService.kt:89`, `:153-167`
  - Dependencies are the PSI of the collected files plus VFS structure changes. The analyzer can also read modules that never become `AlloyFile`s: `.md` modules (`CompUtil.java:262-266`), and files read from disk when no PSI is found. Changes to those are not tracked.
  - **Fix:** document this, or add the corresponding `VirtualFile`s to the dependencies.

- ✅ **The same model can be parsed twice at once** — `src/main/kotlin/com/serranofp/alloy/semantics/AlloyModelService.kt:84-92`
  - `CachedValue` does not prevent two threads from computing the same value. Opening a file typically runs the external annotator, the model inspections and reference resolution in parallel, and each can parse the model (confidence: plausible).
  - **Fix:** make computation single-flight per file, for example with a `ConcurrentHashMap<stamp, Future>` or a per-file lock, as long as cancellation is respected.

- ✅ **Settings page crashes on out-of-range persisted values** — `src/main/kotlin/com/serranofp/alloy/settings/AlloySettingsConfigurable.kt:86-87`
  - `selectedIndex = state.coreMinimization`/`coreGranularity` throws `IllegalArgumentException` for an out-of-range value in a hand-edited or old `alloy.xml`. `analyzerOptions` already clamps these values, but `reset()` does not.
  - **Fix:** clamp in `reset()` as well.

- ✅ **Solver list is filled twice and the callback can outlive the page** — `src/main/kotlin/com/serranofp/alloy/settings/AlloySettingsConfigurable.kt:36-40`
  - When discovery has already finished, `solversLoaded` runs at once through `getNow` and again through `thenAccept` + `invokeLater`.
  - The `invokeLater` callback has no disposal guard, so it can run after `disposeUIResources`.
  - **Fix:** use `if (done) … else thenAccept`, and check that the component is still alive, or pass an expiry condition.

- ✅ **A stop requested just after the solver finds a result throws the result away** — `src/main/kotlin/com/serranofp/alloy/analysis/AlloyAnalysisEngine.kt:235-243`
  - `resultSAT`/`resultUNSAT` call `checkpoint()`. A stop requested right after the solver found an answer therefore turns a finished SAT/UNSAT result into `Stopped`.
  - **Fix:** don't call `checkpoint()` in the `result*` callbacks.

- ✅ **Listeners run while the analysis holds its own lock** — `src/main/kotlin/com/serranofp/alloy/analysis/AlloyAnalysisEngine.kt:124-131`, `:156-164`, `:179-184`
  - `listener(...)` is invoked inside `synchronized(this)`. A listener that blocks on another thread which calls `stop()`/`state`/`end` on the same analysis (for example `invokeAndWait` to an EDT that calls `stop()`) deadlocks.
  - Current listeners avoid this (`AlloyCommandExecution.stop` takes care to call outside its lock), but the contract is fragile.
  - **Fix:** document the restriction in the KDoc of `start`, or deliver events through a single-threaded queue outside the lock.

- ✅ **The stop flag is not shared with wrapped factories** — `src/main/kotlin/com/serranofp/alloy/analysis/StoppableSatFactory.kt:38-41`
  - `doOptions` returns a new `StoppableSatFactory` with its own `stopped` flag. `stop()` on the outer factory leaves it `false`, so solvers created later by the inner factory are not expired. `destroySolverProcesses` also uses the outer `original.executables`.
  - No `doOptions` override exists in pardinus/Alloy 6.2.0, so this is latent today.
  - **Fix:** share the state (for example an `AtomicBoolean` plus the solvers list) between the outer and inner factories.

- ✅ **User-visible strings are not in the message bundle** — the bundle (`src/main/resources/messages/AlloyBundle.properties`) has only 14 keys, for inspections and inlays.
  - **Fix:** move these hardcoded strings into `AlloyBundle`:
    - usage-type and kind names: `AlloyFindUsages.kt:38-50`, `:69-70`, `AlloyStructure.kt:80-89`;
    - rename messages: `AlloyRename.kt:34`, `:43`, `:57-58`;
    - the opened-module error: `AlloyExternalAnnotator.kt:79`;
    - all settings labels: `AlloySettingsConfigurable.kt:24-30`, `:43-52`, `:68-69`, plus `AlloySettings.kt:84`;
    - color-page descriptors: `AlloyColorSettingsPage.kt:46-60`;
    - the file type description: `AlloyFileType.kt:9`;

### Positive notes

- `AlloyModelService.collect` caches the exact PSI text it gave to the analyzer, and every position mapping uses that text, so ranges always agree with the PSI the result is cached on.
- `openedPath` mirrors `CompUtil.computeModulePath`/`up` faithfully, including the `"anything"` boundary case, and the KDoc gives worked examples.
- The grammar keeps PSI flat (it parses only declarations and references), which makes the PSI code simple. Unbalanced brackets only break their own paragraph.
- Stopping an analysis is designed carefully: the reporter checks a flag, SAT4J solvers are expired, and the run is shown as "Stopping" while a long translation finishes. There is exactly one `End` event, and `Disposer` ties analyses to their parent.
- Stub-based declarations with `getName` from the stub keep Go to Symbol and the name index cheap. Locals get a `LocalSearchScope`, which also enables in-place rename.
- `AlloySolvers` puts executables found on the user's `PATH` into pardinus's system properties, which fixes IDEs launched from the desktop.

## `run` and `run/tests`

This package runs Alloy commands inside the IDE. A command runs from its gutter icon as a `Task.Backgroundable`, or as a suite in the SM test runner. Results appear as declarative inlay hints, gutter verdicts and tooltips, and a check can be followed by a vacuity check. `AlloyRunService` makes sure only one analysis runs per project, and `AlloyCommandExecution` is the state machine that turns `AlloyAnalysisEvent`s into `CommandResult`s. Overall quality is high. Responsibilities are split clearly, KDoc is thorough, the locking was clearly thought through (`stop()` calls the analysis outside its own lock, and follow-up analyses that start on a disposed parent are handled), and the log mimics the desktop `SimpleReporter` closely. The main weaknesses:
- how a command is identified (`AlloyCommandRef`),
- missing exception handling on the launch path, which can leave the service busy for good,
- one race that can lose a stop request.

### High

- ✅ **Commands that share a label run the wrong command** — `src/main/kotlin/com/serranofp/alloy/run/AlloyCommands.kt:27-29` (used by `AlloyCommandLauncher.kt:77`, `tests/AlloyCommandsProcessHandler.kt:93-94`, `tests/AlloyTestLocator.kt:38`)
  - **Problem:** `find` picks the *first* command whose label matches and ignores `ref.index`. In Alloy it is very common to check the same assertion at several scopes (`check NoCycles for 3` and `check NoCycles for 6`, or `run show for 3` and `run show for 3 but 5 Int`). All of these get the same label.
  - **Failure:** clicking the gutter of `check NoCycles for 6` makes the launcher find the PSI of the first command and run `check NoCycles for 3`. The `expect` is also read from the first command. The result is then recorded under `("NoCycles", 1)` and shown on the second line with the second command's text, which is silently wrong. In the test runner, both nodes run the first command and both navigate to it. *Rerun Failed* (`matches`, which compares labels only) reruns every command with that label.
  - **Fix:** match by label only when the label is unique in the file. Otherwise use the index, or identify a command by (label, occurrence among commands with the same label).

- ✅ **An exception during launch leaves the execution running forever, so the service stays busy for the rest of the session** — `src/main/kotlin/com/serranofp/alloy/run/AlloyCommandTask.kt:21`, `src/main/kotlin/com/serranofp/alloy/run/AlloyCommandLauncher.kt:47`
  - **Problem:** `launcher.launch` has no `try`/`catch`. `ReadAction.nonBlocking(...).executeSynchronously()` runs under the task's indicator, so it throws `ProcessCanceledException` if the user cancels the task while the model is being parsed. A large model can take seconds to parse. Any `RuntimeException` from `AlloyModelService.model`, `options()` or `engine.execute` (for example, failing to create the 64 MB-stack thread) ends `Task.run` the same way.
  - **Failure:** `finish()` is never called, so `AlloyRunService.active` is never cleared. Every later run, suite or enumeration reports "An Alloy analysis is already running" until the project is reopened, and the gutter keeps spinning.
  - **Same cause in the test runner:** in `tests/AlloyCommandsProcessHandler.kt:112-120` the polling loop never ends unless the user presses Stop. After that, `launched.get()` throws `ExecutionException` out of `runSuite`.
  - **Fix:** wrap `launch` (or its body) in `try { … } catch (e: Throwable) { execution.fail(AlloyRunLog.FAILED, …) }`. For `ProcessCanceledException`, call `execution.terminate()` and rethrow.

### Medium

- ✅ **A stop can be lost while the check hands over to its vacuity check** — `src/main/kotlin/com/serranofp/alloy/run/AlloyCommandExecution.kt:227-234` and `113-120`; `AlloyCommandTask.kt:25-28`; `tests/AlloyCommandsProcessHandler.kt:115-118`
  - **Problem:** `stop()` reads `analysis` (A1) under the lock, then calls `A1.stop()` outside it. In between, A1 can finish `Unsat`, and `startVacuityCheck` then starts A2 and stores it in `analysis`. `A1.stop()` returns early because A1 is already `Done`, so no `Stopping` event is sent and nothing stops A2.
  - **Failure:** both callers set `stopRequested = true` and never call `stop()` again. Cancelling the task or destroying the suite is ignored until the vacuity check finishes on its own, which can take as long as the check itself.
  - **Fix:** keep a `stopRequested` flag in the execution, set under the lock in `stop()`. Check it in `startVacuityCheck`/`solve` (skip the check or stop the new analysis), or re-check `analysis !== running` after the stop and repeat. A simpler alternative: callers call `execution.stop()` on every poll while cancelled; `AlloyAnalysis.stop` is idempotent.

- ✅ **`AlloyCommandRef` equality includes `index`, even for labelled commands** — `src/main/kotlin/com/serranofp/alloy/run/AlloyCommands.kt:15`, `src/main/kotlin/com/serranofp/alloy/run/AlloyCommandResults.kt:115`

- ✅ **Results keep every `A4Solution` and parsed `CompModule` for the whole session** — `src/main/kotlin/com/serranofp/alloy/run/AlloyCommandResults.kt:98`, `:43`

- ✅ **The edit counter is stored on the `Document`, which can be garbage-collected** — `src/main/kotlin/com/serranofp/alloy/run/AlloyCommandResults.kt:112`, `:163-164`
  - **Problem:** `FileDocumentManager` holds documents of unmodified files without editors only weakly. When the document is collected, the `EDITS` counter restarts at 0.

## `inspections`

**Overview.** This package holds the plugin's semantic inspections. They work on the analyzer's type-checked `CompModule` (taken from `AlloyModelService`), not on the PSI. Analyzer `Pos` values are mapped back to PSI ranges through `AlloyInspectionContext`. The package contains:
- a base class (`AlloyModelInspection`) and a per-command layer (`AlloyCommandInspection`);
- a port of the analyzer's `ScopeComputer` (`AlloyCommandBounds`);
- a temporal "frame" analysis (`AlloyFrameAnalysis`);
- seven inspections, a comment-based suppressor, and quick-fixes that edit text directly (`AlloyScopeText`/`AlloyScopeEdit`/`AlloyScopeFix`, `AlloyTextEdits`).

Overall quality is good. The code is compact and well documented. The `ScopeComputer` port follows upstream closely (checked against alloy core 6.2.0 sources). Quick-fixes hold no hard PSI references, and analyzer-built nodes with no token of their own are filtered out with care. The main problems are semantic: one blind spot of the frame analysis around the meta model, one wrong message for `after always`, and a few false positives or negatives. The rest is duplicated per-command work, missing cancellation checks, and small pieces of dead code.

### High

- ✅ **Frame conditions written over the meta model are not seen when the model has no `var sig`** — `src/main/kotlin/com/serranofp/alloy/inspections/AlloyFrameAnalysis.kt:132`, `src/main/kotlin/com/serranofp/alloy/inspections/AlloyMissingFrameConditionInspection.kt:35`
  - **Cause.** `mention()` is only called for fields with `isVariable != null`. Upstream `CompModule.resolveMeta` creates the meta field `value` of `S$f` with the *owner sig's* `isVariable`, not the field's: `kb.addDefinedField(..., s.isVariable, "value", field)`. So for `sig File { var shared: set Token }` with a static `File`, `File$shared.value` is not `var`.
  - **Effect.** The guard at line 35 never fires in such models. `pred share { shared' = ...; all v: var$ - File$shared | v.value = v.value' }` is then reported as missing frame conditions for every other `var` field. It only works in the book model (the test data) because that model has `var sig uploaded`/`trashed`, whose `value` fields are var. A meta-only predicate such as `pred stutter { all v: var$ | v.value = v.value' }` is not recognized as an event at all.
  - **Also.** The `it is Sig && it.isMeta != null` half of line 35 is dead: meta sigs are never `var`, so they never reach `constrains`.
  - **Fix.** In `walk`, treat fields with `x.sig.isMeta != null` (and meta sigs) as mutable, as `AlloyStaticPrimeInspection.isMutable` already does (line 124). Add a test whose model has only `var` fields.

### Medium

- ✅ **`after always P` (and `after eventually`, `after (P until Q)`) is reported as constraining "only the second state"** — `src/main/kotlin/com/serranofp/alloy/inspections/AlloyFactOnlyAtStartInspection.kt:94-101, 140-150`
  - **Cause.** A written `after` is recorded at `depth == 0` before its body is visited. The `always` below it only makes the occurrences *inside* it nested, so `inner` stays empty. The message then becomes "This after constrains only the second state, because the fact is not under always".
  - **Effect.** `fact { after always (x' = x) }` holds from the second state onwards, so the message is wrong.
  - **Fix.** When the `after`'s subtree contains a future operator, word the message as "from the second state on" or skip it. Alternatively, record the `after` only if something non-nested is recorded under it.

- ✅ **Helper "events" called from other events get missing-frame warnings** (plausible; it is how the heuristic is designed) — `src/main/kotlin/com/serranofp/alloy/inspections/AlloyMissingFrameConditionInspection.kt:28-33`
  - **Cause.** Every predicate that satisfies `isEvent` is checked on its own.
  - **Effect.** A common style factors effects into sub-predicates, e.g. `pred moveMsg[m] { inbox' = inbox - m }`, called from `pred send { moveMsg[m]; outbox' = outbox }`. `moveMsg` is flagged for `outbox` even though every call site frames it.
  - **Fix.** Skip events that are only called from other event predicates in the file (collect callees while walking). Alternatively, only report the predicates used as disjuncts under `always` in facts.

- ✅ **Name ambiguity for frame conditions only looks at mutable fields** — `src/main/kotlin/com/serranofp/alloy/inspections/AlloyMissingFrameConditionInspection.kt:53-56`
  - **Effect.** Take `var f` in sig `A` and a *static* `f` in sig `B`. The fix inserts `f' = f`, which the analyzer reports as ambiguous, or resolves to the wrong field.
  - **Fix.** Compute `ambiguous` over all fields of the user's sigs (static included), and also over sig names.

- ✅ **`AlloyWrapInAlwaysFix` changes meaning for initial-state facts** — `src/main/kotlin/com/serranofp/alloy/inspections/AlloyFactOnlyAtStartInspection.kt:173-204`, offered at line 45
  - **Effect.** The fix is offered on `fact init { no inbox }`, where it turns an initial condition into "inbox always empty". It is also offered on mixed facts such as `fact { no inbox  all n | n.inbox' = n.inbox }`, where wrapping the whole body silently strengthens the `init` part. The spec requires this behaviour, so this is a design concern rather than a bug.
  - **Fix.** Lower the fix's priority, or don't offer it for the information-level "no temporal operator" case. For mixed facts, consider wrapping only the offending conjunct.

### Low

- ✅ **Literals below the minimum, hex/underscore literals and leading-zero literals are never reported** — `src/main/kotlin/com/serranofp/alloy/inspections/AlloyIntLiteralRangeInspection.kt:68-72`
  - **Negative literals.** Upstream `CompFilter` folds `-20` into one `NUMBER` constant (value -20) whose pos starts at `-`. The check `x.num > max` ignores it, and `findElementAt` lands on the `-` token, so `#s = -20` at 4 bits goes unreported.
  - **Other forms.** The lexer accepts `0x1F`, `0b101` and `1_000` (`Alloy.flex:156-158`), and the analyzer also parses leading-zero literals such as `007`. The `it.text == x.num.toString()` filter drops all of these.
  - **Fix.** Check `x.num < Util.min(bw)` too. Match the token by position and element type only, and use `x.num` rather than `literal.text.toInt()`.

- ✅ **Bound sources are not updated when `lowerBound` raises a scope** — `src/main/kotlin/com/serranofp/alloy/inspections/AlloyCommandBounds.kt:178-180`
  - **Effect.** With `sig A {}  one sig B, C, D, E extends A {}` and `for 3`, `A` is raised to 4 but its source stays `Overall`. `AlloyUnscopedMutableSignatureInspection` then says "gets the command's default scope of 4".
  - **Fix.** Record the raise, e.g. `Source.Inherited` or a new `Raised` source, or report the pre-raise value.

- ✅ **`AlloyCommandBounds` accepts some commands that `ScopeComputer` rejects** — `src/main/kotlin/com/serranofp/alloy/inspections/AlloyCommandBounds.kt:54-59, 65`
  - **Cases.** A non-exact `3 String` (upstream: "Sig String must have an exact scope"). Bitwidth > 30, and a written `seq` larger than `Util.max(bitwidth)`, are not checked either.
  - **Effect.** The class doc says bounds are null wherever the analyzer would reject the command, but here they are offered anyway.
  - **Fix.** Mirror those three checks in `compute()` (and make `seq` honour validity).

- ✅ **`moduleOf` may name the wrong module** — `src/main/kotlin/com/serranofp/alloy/inspections/AlloyExactParameterScopeInspection.kt:41-45`
  - **Cause.** It takes the first `open` of *any* reachable module whose argument has the same last segment.
  - **Effect.** With `open util/graph[State]` before `open util/ordering[State]`, the message says `util/graph` forces the exact scope. Sigs with the same name in different modules also collide.
  - **Fix.** Only consider modules whose parameter is declared `exactly`, or prefer `util/ordering` (whose parameter is declared `exactly`), and compare resolved sigs rather than strings.

- ✅ **No cancellation checks in AST walks** — `src/main/kotlin/com/serranofp/alloy/inspections/AlloyIntLiteralRangeInspection.kt:28-39, 82`, `src/main/kotlin/com/serranofp/alloy/inspections/AlloyFrameAnalysis.kt:79`, `src/main/kotlin/com/serranofp/alloy/inspections/AlloyStaticPrimeInspection.kt:42`
  - **Effect.** `AlloyIntLiteralRange` re-walks the whole formula (all facts), every signature fact and every called function body once per command, i.e. O(commands × model size), and none of the walks call `ProgressManager.checkCanceled()`. On large models with many commands, typing does not cancel the daemon promptly.
  - **Fix.** Call `checkCanceled()` per root and per command. Precompute the literals reachable from facts and signature facts once and reuse them for every command.
  - **Caveat.** If cancellation is added, `runCatching` at `AlloyCommandBounds.kt:41` would swallow `ProcessCanceledException`. Catch `Err` only.

- ✅ **Per-command recomputation of command-independent data** — `src/main/kotlin/com/serranofp/alloy/inspections/AlloySeqBoundTooSmallInspection.kt:19`, `src/main/kotlin/com/serranofp/alloy/inspections/AlloyUnscopedMutableSignatureInspection.kt:18`, `src/main/kotlin/com/serranofp/alloy/inspections/AlloyCommandInspection.kt:43`
  - **Effect.** `sequenceFields(context)` and `mutableUses(context)` walk all sigs and fields for every command. `AlloyCommandBounds` is also recomputed by each of the four command-based inspections.
  - **Fix.** Compute these once per `check(context, holder)`. Optionally cache the bounds on the `AlloyModelResult.Model` with a `CachedValue` that has the same dependencies as the model.

- ✅ **Concurrent first computation of the model** (plausible; the root cause is outside this scope, in `semantics/AlloyModelService.kt`) — `src/main/kotlin/com/serranofp/alloy/inspections/AlloyModelInspection.kt:35`
  - **Effect.** Seven model inspections, five simplification inspections and the external annotator all call `model()` from parallel daemon threads. `CachedValue` does not serialize computation, so on a cold cache the analyzer may parse the same model several times concurrently. That wastes CPU, and it is risky given the analyzer's static state.
  - **Fix.** Make the service compute under a per-file lock, or use `CachedValuesManager.getCachedValue` with a `RecursionGuard`/`ConcurrentMap` of in-flight futures.

- ✅ **The fact inspection reports primes on static expressions** — `src/main/kotlin/com/serranofp/alloy/inspections/AlloyFactOnlyAtStartInspection.kt:103-117`
  - **Effect.** `fact { succ' = succ }` with a static `succ` gets "constrains only the transition out of the first state" on top of the static-prime warning. This is inconsistent with the spec's "`'` on an expression that mentions a mutable relation", which `AlloyFrameAnalysis` follows.
  - **Fix.** Record only when the primed expression mentions a mutable relation, e.g. with `analysis.summary(x.sub).mentions.isNotEmpty()`.

- ✅ **User-visible strings are hardcoded** — every inspection message and every `getText()`/`getFamilyName()`, e.g. `src/main/kotlin/com/serranofp/alloy/inspections/AlloyStaticPrimeInspection.kt:89-99` and `src/main/kotlin/com/serranofp/alloy/inspections/AlloyInspectionSuppressor.kt:47`.
  - **Context.** `messages/AlloyBundle.properties` exists but there is no `AlloyBundle` class. Only the `plugin.xml` display names use it.
  - **Fix.** Add a `DynamicBundle` and move messages and fix names there. Family names should be constant, not parameterized as in `"Suppress for $kind"`, `"Add $it"` or `"Set the bitwidth of … to N int"`.

- ✅ **The default bitwidth of 4 is duplicated in three places** — `src/main/kotlin/com/serranofp/alloy/inspections/AlloyCommandBounds.kt:57`, `src/main/kotlin/com/serranofp/alloy/inspections/AlloySeqBoundTooSmallInspection.kt:30`, `src/main/kotlin/com/serranofp/alloy/inspections/AlloyIntLiteralRangeInspection.kt:29,103`
  - **Fix.** Expose `bitwidth` (and `maxInt`) on `AlloyCommandBounds` and use it everywhere.

### Nit

## `simplifications`

**Overview.** This package holds the five "… can be simplified" inspections (`AlloySimplificationInspection` and its subclasses) and the seven equivalence intentions (`AlloyRewriteIntention`). Both work on the analyzer's type-checked AST:

- `AlloyRewriteWalker` walks facts, assertions, function bodies and sig facts, and tracks the precedence position (`AlloyPosition`) of each node.
- Rules (`Alloy*Rules`, `AlloyNegation`) build `AlloyPiece` trees.
- `AlloyRewriteRenderer` prints those trees with only the parentheses they need.
- `AlloySourceText` maps AST nodes back to balanced, parenthesis-widened text ranges.
- `finish()` acts as a safety net: it rejects any rewrite that would drop comments or tokens other than the operators of the nodes it uses.

The design is careful and well documented. The Alloy semantics of the rules themselves are correct: I checked De Morgan, the temporal dualities, `^r + iden`, the transpose/join swap, `disj` and membership. The weak spot is the precedence and position model, where two cases produce rewrites that change the meaning of the model (both reproduced with a temporary test, since removed). Threading is mostly right, but one cache is shared across threads without synchronization.

### High

- ✅ **A rewrite before `;` can absorb the rest of the sequence** — `src/main/kotlin/com/serranofp/alloy/simplifications/AlloyRewriteWalker.kt:224-229`
  - **Cause:** `p ; q` is parsed by `CompParser` as `ExprBinary.Op.AND.make(o, null, p, AFTER(q))`, an AND list whose `pos` is at `;`. `listPosition` treats any token after an operand that is not `and`/`&&` as a block-line break (`lineAfter`), so the operand before `;` gets `rightOpen = true` and `bindAllowed = true`. But in Alloy's grammar, a quantifier body takes in the `;` that follows it (`SuperOrBar ::= BAR ExprNoSeq TRCSEQ Expr`), so a quantifier or `let` placed there without parentheses swallows `; q`.
  - **Reproduced:** `pred subject { not (some n: Node | n in n.succ) ; p }` becomes `no n: Node | n in n.succ ; p` after the "Negated quantifier" quick-fix. That now means `no n | (n in n.succ ; p)`. The intention "Move negation into quantifier" is affected the same way, as is any slice that `endsOpen`. It also happens when `;` follows a flattened `a and b`.
  - **Fix:** in `listPosition`, when `after` (or `before`) is `AlloyTypes.SEMICOLON`, keep the SEQ level but set `rightOpen = false`. Alternatively, treat `;` as a separator for an AND list whose `pos` is at `;`. Add a regression test.

- ✅ **The receiver of a method-style call `e.f` is treated as if it were inside brackets** — `src/main/kotlin/com/serranofp/alloy/simplifications/AlloyRewriteWalker.kt:204`
  - **Cause:** `CompModule.process` resolves `e.f`, where `f` is a fun/pred, into `ExprCall(f, [..., e])`. So at least one argument is written before a `.`, outside any brackets. `operands()` nevertheless gives every `ExprCall` argument `AlloyOperandSpec.BOUNDED` (level SEQ, right-open), so a replacement there loses its parentheses.
  - **Reproduced:** with `fun g[s: Node -> Node]: set Node {…}`, `some (Node->Node + Node->Node).g` becomes `some Node->Node.g` after the idempotence fix. That parses as `Node -> (Node.g)`: the meaning changes, or the model stops type-checking.
  - **Fix:** for an argument whose source range lies before the call's identifier token (or before the `[`), use the left-of-dot spec `AlloyOperator.JOIN.operand(0, 2)` (BRACKET level, not right-open). Keep BOUNDED only for the arguments inside the brackets.

### Medium

- ✅ **The cache shared by the intention index is not thread-safe** — `src/main/kotlin/com/serranofp/alloy/simplifications/AlloySourceExpr.kt:45,88-97`, `src/main/kotlin/com/serranofp/alloy/simplifications/AlloyRewriteIndex.kt:32-36`
  - **Cause:** `AlloyRewriteIndex` is cached statically per `CompModule`, and its entries keep one `AlloySourceText`. Its `sources` field is a plain `IdentityHashMap`. The index is then used from `isAvailable` (BGT in current platforms), `generatePreview` (BGT) and `invoke` (EDT). Rule matching still fills `source()` with nodes not seen during the build, for example `source.source(x)` for declared variables in `distinctVariables` and `source.source(list)` in `listPosition`.
  - **Risk:** concurrent `put`s into `IdentityHashMap` can corrupt its open-addressing table, causing lost entries or, after a racing resize, an endless probe.
  - **Fix:** use a `ConcurrentHashMap` keyed on identity (wrap the key), or a synchronized map. Alternatively, fill the cache fully at build time and make it read-only afterwards. (Confidence: plausible. The race window is real, but I did not reproduce it.)

- ✅ **The walker never checks for cancellation** — `src/main/kotlin/com/serranofp/alloy/simplifications/AlloyRewriteWalker.kt:116`
  - **Cause:** `visit` recurses over every node. For each node it calls `isWritten`/`source`, which scans the leaves of the node's range in `balance` and `tokens`. There is no `ProgressManager.checkCanceled()` anywhere in the path. PSI calls like `findElementAt`/`nextLeaf` do not check for cancellation either.
  - **Impact:** on large models each of the five inspections (plus the index build) runs to completion even after the user has typed, which delays restarting highlighting.
  - **Fix:** call `ProgressManager.checkCanceled()` at the top of `visit` and inside the loop in `tokens()`.

- ✅ **The intention's `isAvailable` may trigger a full analysis** — `src/main/kotlin/com/serranofp/alloy/simplifications/AlloyRewriteIntention.kt:48`
  - **Cause:** off the EDT, `availableModel` falls back to `AlloyModelService.model()`, which parses and resolves the whole module set. The class comment says the intention only reuses the model highlighting already computed, but that holds only on the EDT. When the caret moves before highlighting finishes, the intention popup computation pays for a full Alloy analysis.
  - **Fix:** always use `cachedModel(file)` in `find()` and return null when it is absent. That matches the documented contract.

### Low

- ✅ **Fix-all can apply stale offsets** — `src/main/kotlin/com/serranofp/alloy/simplifications/AlloySimplificationInspection.kt:46-53`
  - `textRangeInElement` is relative to the paragraph start, captured when the problem was reported. After one fix shortens the paragraph, later fixes in the same paragraph check `document.getText(range) == original` at the old offsets.
  - Usually this check fails and the fix silently does nothing, so "Fix all" handles one problem per paragraph per run. With repetitive text, the shifted range could match a different occurrence, whose parenthesization context may differ.
  - **Fix:** take the range from `descriptor.textRange` (backed by a range marker in the platform's descriptor), or store a `RangeMarker` in the fix. (Confidence: plausible.)

- ✅ **Operands with no source are skipped entirely after a match** — `src/main/kotlin/com/serranofp/alloy/simplifications/AlloyRewriteWalker.kt:132`
  - `?: continue` skips any operand whose source cannot be mapped, so its subtree, which may contain mappable nodes, is never visited. For example, the inner `ExprLet` of `let a = x, b = y | …` returns null from `ownRange`.
  - **Fix:** visit the operand when its range is unknown. Visiting is safe because results are only produced for nodes with a source.

- ✅ **`adjacentConjuncts` stops at the first matching pair** — `src/main/kotlin/com/serranofp/alloy/simplifications/AlloySimplificationRules.kt:68-74`
  - It returns the first pair that `combine` accepts. If `finish` then rejects that pair (for example because a `}` lies between flattened block lines), later valid pairs in the same list are never tried.
  - **Fix:** pass a validation callback, or let the walker try every candidate.

- ✅ **Shift operators get the wrong precedence level** — `src/main/kotlin/com/serranofp/alloy/simplifications/AlloyPrecedence.kt:51` and the `BINARY` map at `AlloyPrecedence.kt:186-198`
  - `SHL`/`SHA`/`SHR` are missing from `AlloyOperator.BINARY`, so they fall into `else -> COMPARE` instead of `SHIFT`. The only effect is extra parentheses, for example as the right operand of a comparison or `some`.
  - **Fix:** map them to `SHIFT`.

- ✅ **"Swap join with transpose" can produce a double transpose** — `src/main/kotlin/com/serranofp/alloy/simplifications/AlloyEquivalenceRules.kt:181-185`
  - The `r.e → e.~r` branch wraps the left side in `TRANSPOSE` even when it already is one, so `(~s).e` becomes `e.~~s`, which the Relational inspection then flags.
  - **Fix:** when `join.left` is a written transpose, slice its `sub` directly, with the transpose added to `uses`.

- ✅ **The intention index lives in a static map** — `src/main/kotlin/com/serranofp/alloy/simplifications/AlloyRewriteIndex.kt:32-36`
  - The global `WeakHashMap<CompModule, AlloyRewriteIndex>` strongly holds the `AlloyFile`, `Document`, paragraph PSI and AST, and lives outside any project lifecycle. `getOrPut` on a `synchronizedMap` is not atomic either, so two threads may build the index twice.
  - There is no leak today, because AST nodes do not reference `CompModule`. Still, attaching the index to the model's `CachedValue` (or to `AlloyModelResult.Model`) would tie it to the right lifetime and avoid the global.

- ✅ **Five full walks per highlighting pass** — `src/main/kotlin/com/serranofp/alloy/simplifications/AlloySimplificationInspection.kt:18`
  - Each of the five inspections builds its own `AlloySourceText` and walks the whole model, recomputing the same `balance`/`widen` ranges, and the intention index does it a sixth time.
  - **Fix:** share one `AlloySourceText` per module, as the index already does.

- ✅ **User-visible strings are hardcoded** — for example `src/main/kotlin/com/serranofp/alloy/simplifications/AlloySimplificationInspection.kt:44`, `AlloyRewriteIntentions.kt:3-15`, and the messages and fix names in every `*Rules.kt`.
  - `messages/AlloyBundle.properties` exists but only holds the inspection display names. Problem descriptions, fix names, family names and the intention texts all bypass it.
  - The same strings are also repeated: the intention family names are duplicated in the test harness, and `DE_MORGAN` appears twice.
  - **Fix:** move them into the bundle.

### Nit

- ✅ **Duplicated code:**
  - `bind()` is duplicated in `AlloyEquivalenceRules.kt:62-65` and `AlloyQuantifierRules.kt:19-22`, and both files also have similar `quantifier()` helpers.
  - The `COMPARISONS` array in `AlloyBooleanRules.kt:11-15` repeats the keys of `NEGATED_COMPARISONS` (`AlloyNegation.kt:8`).
  - `AlloySimplification` and `AlloyEquivalence` (`AlloySimplificationRules.kt:9-26`) are identical apart from `kind`; a single class with a `kind` parameter would do.
- ✅ **Unused metadata:**
  - `AlloyRewriteFamily`, `AlloyRewriteRule.family`/`kind` and `AlloyRewriteResult.rule`/`node` (`AlloyRewrite.kt:8-24,53-61`) are never read by production code.
  - `AlloyRewriteContext.ancestors`/`parent` are only used by a test, yet `ancestors + node` copies the ancestor list at every level (`AlloyRewriteWalker.kt:133,139`).
- ✅ **Early exit in `distinctVariables`** — `AlloyQuantifierRules.kt:96`: `return@AlloySimplification null` inside the `rest.map` aborts the whole rule, where the loop uses `continue` everywhere else.
- ✅ **Redundant parentheses kept:** slices keep the parentheses they were written in even when the new position does not need them. For example, `always (always p)` becomes `(always p)` (`AlloyTemporalRules.kt:18`), and `not (not (a or b))` at the top level becomes `(a or b)`.
- ❎ **Over-cautious `endsOpen`** — `AlloyRewriteWalker.kt:79`: it returns true for every non-comprehension `ExprQt`, including `all x: A { p }`, whose closing `}` already ends it. This only adds unneeded parentheses. *Not a problem:* in `CompParser` a quantifier only appears as the last operand of the `…A` rules, so `all x: A { p } and q` does not parse and the parentheses are needed; the KDoc of `opens()` now says so.
- ✅ **Inconsistent token-type access:** `elementType` and `.node.elementType` are mixed in `AlloySourceExpr.kt` and `AlloyRewriteWalker.kt`.

### Positive notes

- `finish()` is a strong safety net: a rewrite cannot drop comments, or tokens that do not belong to its used nodes or discarded operands. This keeps most rule bugs from destroying text.
- Bracket balancing and parenthesis widening (`balance`/`widen`) handle the analyzer's truncated spans cleanly, and are documented with examples.
- The rules respect subtle Alloy semantics: `after`/`before` are excluded from idempotence, `before` has no dual, `implies … else` (`ExprITE`) is left alone, membership requires a single `one`-bounded variable that does not occur in `B`, and `!=`/`not in` are not taken for logical operators when choosing the operator style.
- Macro expansions and nodes from other files are excluded consistently through `elsewhere`/`inParagraph`, and so are block lines with no written `and`.
- The quick-fix checks the document text before editing, and the intention preview uses `CustomDiff` on the original file instead of re-running on a copy that has no model.

## `viewer`

**Overview.** This package is the "Alloy Instance" tool window:
- `AlloyInstanceViewer` is the project service that holds the session and asks for New Config, Trace, Init and Fork.
- `AlloyInstancePanel` provides the Visualization, Text and Table tabs, the toolbar and the projection selectors.
- `AlloySolutionModel` wraps `A4Solution`/`VizState`.
- The trace path strip is `AlloyTraceStrip` plus `TraceStripLayout`, and `TraceDiff` produces the Text-tab diff.
- The dark-theme recolouring of the Alloy graph is in `DarkGraphics`, `DarkColors` and `DarkGraphLayerUI`.
- The evaluator is a fragment field with completion, a watches tree and a single-thread runner, with watches persisted in the workspace.

The code is compact and well documented, and it follows the Alloy desktop semantics closely (fork codes, the lasso, `toString`/`format`). The main problems are:
- a real memory leak in how graph panes are wrapped;
- the evaluator queue doing work nobody will see, and possibly showing "Evaluating…" forever;
- heavy analyzer work (XML writing, parsing, magic layout, diffs) running on the EDT;
- several small robustness gaps.

User-visible strings are hardcoded throughout. That matches the rest of the codebase, which has no `AlloyBundle` class.

### High

- ✅ **Shared `LayerUI` keeps a strong reference to every graph pane ever created** — `src/main/kotlin/com/serranofp/alloy/viewer/AlloyInstancePanel.kt:276` (with `darkGraphs` at `:87`).
  - **Problem:** `graphPane()` wraps each new canvas in `JLayer(canvas, darkGraphs)` around one shared `DarkGraphLayerUI`. The JDK's `LayerUI.installUI` calls `addPropertyChangeListener((JLayer) c)`, and that is only undone by `uninstallUI`, which runs only when the layer's UI is replaced. The removed `JLayer`s are never given a new UI.
  - **Effect:** the shared `LayerUI`'s `PropertyChangeSupport` holds every `JLayer`, and through it every `GraphCanvas` and `GraphViewer`. `redrawGraph()` runs on every state step, projection change, atom choice and new solution, and makes 1–2 graphs each time.
  - **Scenario:** stepping through a 20-state trace 10 times keeps about 400 graph viewers alive until the tool window is disposed.
  - **Fix:** either create a new `DarkGraphLayerUI` per pane and share only the palette (for example a holder object that the theme listener resets), or call `layer.setUI(null)` on the old layers in `AlloyStatePanes.show()` before `removeAll()`.

### Medium

- ✅ **The evaluator runs superseded requests that are still queued** — `src/main/kotlin/com/serranofp/alloy/viewer/AlloyEvaluator.kt:59-61`.
  - **Problem:** `invalidate()` only stops results from being delivered. Tasks still waiting in the one-thread executor check `disposed` but not `generation`, so each one still runs a full Kodkod evaluation.
  - **Scenario:** with 5 watches, clicking through 10 states in the strip queues 50 evaluations, and all of them run in order before the 5 that matter. The panel shows "Evaluating…" for the whole time.
  - **Fix:** make `generation` an `AtomicLong` (or `@Volatile`) and skip the task when `submitted != generation` before calling `evaluate`.

- ✅ **An evaluation that throws a non-`Err` exception leaves its row on "Evaluating…" forever** — `src/main/kotlin/com/serranofp/alloy/viewer/AlloyEvaluator.kt:61` and `AlloySolutionModel.kt:145-149`.
  - **Problem:** `evaluate` catches only `HigherOrderDeclException` and `Err`. Anything else escapes `executor.execute`, `deliver` is never called, and `node.result` stays `null` (`isEvaluating()` stays true).
  - **Likely cause:** a `StackOverflowError` or `OutOfMemoryError` on a deep or huge expression. The evaluator runs on a pool thread with the default stack, while `AlloyAnalysisEngine` deliberately starts analyses on a thread with a large `STACK_SIZE`.
  - **Fix:** in the runner, catch `Throwable` (rethrowing control-flow exceptions) and deliver `EvaluationResult.Error`. Also consider running evaluations on a large-stack thread, as the analysis engine does.
  - Confidence: plausible.

- ✅ **Building and showing a solution blocks the EDT** — `AlloyInstanceViewer.kt:145`, `AlloyInstanceViewer.kt:265`, `AlloySolutionModel.kt:30,45-55,66`, `AlloyInstancePanel.kt:201-216`.
  - **What runs on the EDT:**
    - `AlloySolutionModel` writes the whole solution as XML in its constructor. That constructor runs on the EDT in `open()` (an inlay click) and inside `invokeAndWait` in `finished()`.
    - The first `rebuild()` then does the lazy `vizState`: an XML parse plus `AlloyIdeMagic.magic`.
    - Every `stateChanged()` parses a state, runs `TraceDiff.of` (which evaluates every sig, field and skolem; `eval(Field)` has no cache in Alloy 6.2), `format` twice and `getGraph` twice.
  - **Effect:** large instances or long traces freeze the UI.
  - **Fix:** build the model and warm `vizState`/`instance(0)` on the background thread (inside the enumeration task, and in a `Task`/coroutine for `open`). Create only the `RangeMarker` on the EDT. Cache the per-state `diff`/`table` in the model.

- ✅ **Cleanup of an enumeration that never started** — `src/main/kotlin/com/serranofp/alloy/viewer/AlloyInstanceViewer.kt:212-252`.
  - **Problem:** `run.startEnumeration()` and `enumerating = true` happen before the task is queued, and they are undone only in the `finally` inside `Task.run`.
  - **Scenario:** the background task is cancelled, or the project closes, before `run` is entered. `AlloyRunService` would then stay busy: every later command reports `BUSY_MESSAGE`, and the toolbar stays disabled.
  - **Fix:** move the reset into `onFinished()`, which the platform always calls, or start the enumeration inside `run`.
  - Confidence: plausible.

### Low

- ✅ **PSI offsets used with possibly uncommitted documents** — `AlloyInstanceViewer.kt:159,167`.
  - **Problem:** `document.getLineNumber(element.textRange.startOffset)` and `createRangeMarker(...)` mix offsets from the PSI with the live document, without `commitDocument` or an `isCommitted` check.
  - **Scenario:** if the user deletes text and clicks the result inlay before the commit, the offset can be past `textLength`, which throws `IndexOutOfBoundsException`, or the line is wrong.
  - **Fix:** commit the document first (this is on the EDT), or compute the line from the `RangeMarker`.
  - The two separate `AlloyCommands.find` lookups in `origin()`/`anchor()` should also be merged.

- ✅ **The header's line number goes stale** — `AlloyInstanceViewer.kt:188`.
  - **Problem:** `origin.line` is fixed when the session opens, while `commandOffset` follows edits, so after inserting lines above the command the header says "(line 12)" but navigates elsewhere.
  - When the command is not found the header reads "(line 0)".
  - **Fix:** compute the line from `commandOffset` when it is valid.

- ✅ **Fragment marker stored on the `PsiFile`** — `AlloyEvaluatorFragment.kt:26`.
  - **Problem:** the `ALLOY_EVALUATOR_FRAGMENT` user data sits on the PSI file made by `createFileFromText`. If that PSI is rebuilt (reparse, `FileContentUtil.reparseFiles`, dropped caches), the marker is lost.
  - **Effect:** the fragment would get module-level syntax errors, inspections and the normal completion.
  - **Fix:** put the key on `file.viewProvider.virtualFile` (a `LightVirtualFile`) or on the `Document`, and read it from there in `isAlloyEvaluatorFragment`.
  - The guard is also repeated in six callers outside this package. One central check, such as a dedicated fragment language or file type, would be sturdier.
  - Confidence: plausible.

- ✅ **Panel `session` is read off the EDT without volatility** — `AlloyEvaluatorPanel.kt:58,76`.
  - **Problem:** the lambda `{ session?.model }` is called from the completion contributor on a background read thread, but `session` is a plain field written on the EDT.
  - **Fix:** mark it `@Volatile`.

- ✅ **`A4Solution` is not thread-safe, but the model only locks the module** — `AlloySolutionModel.kt:135`.
  - **Problem:** evaluations lock the `CompModule`, but the same `A4Solution` is used at the same time on the EDT (`toString`, `format`, `TraceDiff.of`). Its Kodkod `Evaluator` keeps a shared `wasOverflow` field, and its `evalCache` is an unsynchronized `LinkedHashMap`.
  - **Scenario:** an integer watch evaluating while the EDT computes the diff of an `Int` skolem can get, or lose, a spurious " (OF)".
  - **Fix:** lock on the solution, or document the assumption.
  - Confidence: plausible (a narrow window).

- ❎ **The successor pane reuses the current state's projected atoms** — `AlloyInstancePanel.kt:241-246`. *Not a problem:* `VizState.canProject` refuses mutable types, so only static signatures can be projected and their atoms are the same in every state; a comment and a test document this.
  - **Problem:** with a `var` signature projected, the `AlloyProjection` atom chosen from state *i* may not exist in state *i+1*, and the second graph is built with that atom anyway.
  - **Fix:** check the atom against `next.originalInstance`, or fall back per pane.
  - Confidence: plausible.

- ✅ **Watches are lost when a file moves or is temporarily missing** — `AlloyEvaluatorState.kt:33,46`.
  - **Problem:** watches are keyed by `file.url`, so renaming or moving the file loses them. `loadState` also drops entries whose file `findFileByUrl` cannot find at load time, for example a VFS not yet refreshed or an unmounted path.
  - **Fix:** follow VFS move/rename events, or prune lazily instead of on load.

- ✅ **Global document listener on every keystroke** — `AlloyInstancePanel.kt:143-145`.
  - **Problem:** `updateHeader()` runs for changes to any document in the IDE, including the evaluator's own field, and calls `outdated()` (a read action) three times each time.
  - **Fix:** filter on `event.document` being the session file's document.

- ✅ **Dead code in the production sources (used only by tests)**:
  - `DarkGraphLayerUI.wrap`/`themeChanged` (`DarkGraphLayer.kt:31,45`)
  - `AlloySolutionModel.next`/`previous`/`transitions` (`:79-88`)
  - `AlloyInstanceViewer.stopEnumeration` (`:257`)
  - `TraceDiff.Line.kept`/`added`/`removed` (`:23-25`)
  - `AlloyStatePanes.captions`

  Mark them `@TestOnly`/`internal`, or remove them. The lack of keyboard stepping through states (only mouse clicks on the strip) suggests `next`/`previous` were meant to be wired up.

### Nit

- ✅ **`create()` maps the background colour twice** — `DarkGraphics.kt:72-74,87-90`. A child created with `create()` runs `init` with the delegate's already-mapped background and maps it again. Only the field is reset afterwards, so `clearRect` on child graphics uses `fill(fill(bg))`. Fix: skip the `init` mapping in `create()` (for example a private constructor flag).
- ✅ **Odd completion prefix characters** — `AlloyEvaluatorCompletionContributor.kt:40`. `isNamePart` accepts `"`, which never appears in Alloy names, so a prefix like `"abc` is computed inside strings. *Partly not a problem:* `"` is a valid non-initial name character in the lexer, so it stays; prefixes now start at a valid name start, and `'` was removed.
- ✅ **Duplicated successor rule** — `TraceStripLayout.kt:24` repeats `AlloySolutionModel.successor` (`:82`). Pass `model.successor()` in from `AlloyTraceStrip.show`.
- ✅ **Awkward session construction** — `AlloyInstanceViewer.kt:265,273` builds a `ViewerSession` with a `null` anchor and then copies it in `withAnchorOf`. Create the anchor directly.
- ✅ **Header code that does nothing** — `AlloyInstancePanel.kt:187` sets `header.isEnabled = true` on every update but never disables it.
- ✅ **History browsing discards typed text** — `AlloyEvaluatorPanel.kt:154`. `historyUp` drops whatever is being typed; the debugger's field keeps it as the "current" entry.
- ✅ **Plain Swing fonts** — `AlloyTextPane.kt:21` and `AlloyInstancePanel.kt:153` use `Font(Font.MONOSPACED, …)`. Prefer the editor font (`EditorColorsManager…getFont(EditorFontType.PLAIN)`) or `JBFont`.
- ✅ **Strip clicks can be missed** — `AlloyTraceStrip.kt:54` uses `mouseClicked`, which does not fire if the mouse moves slightly between press and release. Use `mouseReleased`/`mousePressed`.
- ✅ **Hand-made popup trigger** — `AlloyInstancePanel.kt:273` checks buttons by hand. Use `PopupHandler` or `isPopupTrigger`.
- ✅ **Diff built one insert at a time** — `AlloyTextPane.showDiff` inserts into the live `StyledDocument` piece by piece, firing an event per piece. Build a `DefaultStyledDocument` first and then set it.
- ✅ **Watch prompt has no completion** — `AlloyEvaluatorPanel.kt:294` uses a plain `Messages.showInputDialog`, so editing a watch has no Alloy completion, unlike the main field.

### Positive notes

- The generation-based supersession in `AlloyEvaluatorRunner` is simple and correct for delivery, and disposal is checked on both sides.
- Fork codes (-1/-2/-3/0/state+1), the lasso shape, the loop-state tooltip and the Text/Table output follow the Alloy desktop app (`VizGUI`, `A4Solution.toString`/`format`) closely, and the KDoc says where each comes from.
- The geometry (`TraceStripLayout`) and the colour maths (`DarkColors`) are pure and testable, kept apart from Swing.
- Listeners use `messageBus.connect(parent)` and `Disposer` consistently. Persistent state uses `SimplePersistentStateComponent` in the workspace file, which is the right place for per-user watches.
- `outdated()` is documented as callable from any thread and wraps its read in a read action.
