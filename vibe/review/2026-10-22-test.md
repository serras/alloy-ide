# Test review: `src/test/kotlin` (2026-10-22)

**Scope.** This review covers the tests under `src/test/kotlin/com/serranofp/alloy`: 98 files, about 10,000 lines, 771 test methods. It also covers the `src/test/testData` they use. It was done at commit `39d84ac`. Production code, grammar and OpenSpec specs were read only for context.

The review focuses on how much ground the tests cover: whole classes of potential problems as well as the happy paths. A key check: for each bug in the [production review](2026-10-22-main.md), would some test catch it?

Findings were checked by reading the tests and the code they exercise. Findings marked *plausible* follow from reading the code but were not run.

## Summary

The suite is **good on the happy path and weak on the adversarial side**.

**Strengths:**
- **The analyzer is often the oracle,** rather than hand-written expectations:
  - rewrite equivalence is checked with SAT4J (`AlloyRewriteEquivalenceTest`);
  - re-parse ASTs are compared in `AlloyRewriteRenderTest`;
  - `AlloyCommandBounds` is checked against `ScopeComputer` over the Practical Alloy book;
  - viewer text is compared with `A4Solution.toString`/`format`;
  - log lines are compared with recorded `SimpleReporter` output.
- **Assertions are mostly exact,** using `(text, message)` lists, full log lines, exact offsets and `single()`, rather than `contains`/non-empty.
- **Two corpus tests act as regression nets:** the bundled `util/*` modules and 192 Practical Alloy models. They catch grammar regressions, analyzer-integration regressions and false positives of inspections and simplifications on real models.
- **Concurrency paths are exercised with real threads,** using latch-gated `@TestOnly` hooks (`AlloyModelService.parse`, `runner.evaluate`, `viewer.fork`, gated vacuity follow-ups) rather than sleeps.
- **Most positive tests have a negative counterpart.** Examples: binders out of scope, private names hidden, macro expansions not rewritten, nothing completed in comments.

**The main problem:** of the High and Medium bugs in the production review, **essentially none would be caught by the current suite**. There are recurring reasons for that.

1. **Tests use only the simplest shape of each input.** Most production bugs are context or shape edge cases:
   - a rewrite followed by `;` or used as the receiver of `e.f`;
   - a model with `var` fields but no `var sig`;
   - two commands sharing a label;
   - a command inserted above another;
   - `after always`;
   - nested brackets in a bound;
   - a field with `var` before its doc comment;
   - later binders `all x: A, y: x.next`;
   - renaming to a keyword.

   Each feature has one or two simple examples and no table of awkward variants.
2. **Some tests pin the buggy behaviour as the specification.** A correct fix would turn them red, which discourages the fix:
   - `testLabelWinsOverAStalePosition`, `AlloyTestLocatorTest`, `testCommandsAreFoundByLabelWhenTheyMoved`: label-only command lookup;
   - `AlloyCommandResultHintsProviderTest.kt:211`: the hint is not clickable during the vacuity check;
   - `AlloyEvaluatorRunnerTest`: superseded evaluations still run;
   - `testMissingFilesArePrunedOnLoad`: eager pruning of watches;
   - the history test: typed text discarded;
   - tests that keep redundant parentheses.
3. **Oracles miss real failure modes.**
   - "Problem gone after the fix" (`assertEmpty(problems())`) also passes when the fix introduces a type error, because model inspections report nothing on a model that does not type-check. This pattern appears in about 15 tests.
   - Rewrite equivalence is checked only for a formula alone, so the surrounding context never matters.
   - The corpus checks only that a fix type-checks; a meaning-changing rewrite still type-checks.
   - `testCancellationIsNotCaught` fakes a bare `ProcessCanceledException`. The real `CompUtil` wraps it in `ErrorFatal`, so the test is green while that bug is live.
   - `assertNotOffered` filters intentions by a hard-coded copy of the family names, so it passes vacuously if they change.
4. **Failure injection is missing.** Nothing makes these throw:
   - the launch path (`options()`, `engine.execute`), or a cancellation during `find()`;
   - the evaluator, with a non-`Err` throwable;
   - the enumeration `fork`;
   - the parse, under a cancelled indicator.

   So the "run service busy forever" and "Evaluating… forever" bugs are invisible. Cancel tests call `task.run(indicator)` outside `ProgressManager`, so the indicator is never bound to the non-blocking read action.
5. **Threading and cancellation contracts are not asserted.** No test does any of these:
   - run `model()` under a cancelled indicator;
   - check that intentions are not offered before highlighting computed the model;
   - check that heavy viewer work happens off the EDT;
   - count concurrent parses;
   - check that the walkers honour `checkCanceled`.
6. **Tests drive test-only methods instead of production paths.** Examples are `AlloySolutionModel.next/previous/transitions`, `viewer.stopEnumeration()` (production cancels the indicator), `DarkGraphLayerUI.wrap` with a fresh UI per layer (production shares one, which is the leak), and `AlloyMagicLayoutTest`'s copy of the layout pipeline.
7. **Shared state and flakiness.**
   - Solver discovery leaves `alloy.native.exe.*` system properties set across the JVM, and one settings test resolves solvers from the developer's real `PATH`. `testWithoutExecutablesOnlySat4j` therefore depends on test order and on what is installed.
   - Light-project services are not fully reset (`AlloyRunService`, `selectedTab`).
   - `AlloyDesktopPreferencesTest` writes the developer's real `java.util.prefs`.
   - There are timing assertions: `Thread.sleep(200/300)` with a `< 2_000 ms` bound in `AlloyAnalysisEngineTest`, and a `sleep(50)` in the runner disposal test, which can pass vacuously.
   - Some pixel tests depend on fonts.
   - `StoppableSatFactoryTest` is POSIX-only.

**Infrastructure.** The build has no coverage tool (Kover/JaCoCo) and the repo has no CI workflow. Adding Kover would make the coverage maps below measurable rather than estimated, and would point at untested branches mechanically.

### Production-review bugs and their test status

| Production bug (see `2026-10-22-main.md`) | Caught today? | Missing test |
|---|---|---|
| Rewrite before `;` absorbs the sequence | No | Equivalence harness with context `X ; p` |
| Receiver of `e.f` treated as bracketed | No | Context `(X).g`, e.g. `(S->S + S->S).g` |
| Duplicate command labels | No (pinned the other way) | Two `check a` commands, run the second |
| Launch exception leaves service busy | No | `options = { error("boom") }` / PCE, then the next `startRun` succeeds |
| Uncancellable parse / PCE cached as `Unavailable` | No (fake hides it) | `ErrorFatal(cause = PCE)`; real parse under a cancelled indicator |
| Shared `LayerUI` leak | No | Step a trace 10× and bound the listener count |
| Meta-model frame conditions without `var sig` | No | Model with only `var` fields, `all v: var$ - …` |
| Rename to a keyword | No | `renameElementAtCaret("sig")` |
| Stop lost at the check→vacuity handover | No | Pre-ended A1, `stop()`, late `Unsat` |
| Solver kill not scoped | No | A foreign process with the same name survives |
| `after always` message | No | `fact { after always (x' = x) }` |
| Ambiguous frame-condition fix | No (`contains` + `assertEmpty`) | `var f` in A and static `f` in B, then the model must type-check |
| Index shift after an insertion | No | Insert a command above, the hint follows |
| Evaluator supersession and non-`Err` throwable | No (supersession pinned) | Queued requests skipped; a `Throwable` delivers `Error` |
| Documentation signature cut | No | Table: `set (A + B)`, `B[y, z]`, enum, let |

### Recommended actions (in priority order)

1. **Add the missing oracles.**
   - A shared `assertTypeChecks()` after every quick-fix and intention.
   - A *contextual* equivalence harness for rewrites: compare `pred before { CTX(X) }` with `pred after { CTX(X') }` for contexts `X ; p`, `(X).g`, `q and X`, `X implies r`, `let y = A | X`, and `… else`.
   - Apply every equivalence rule and inspection fix to the corpus and check that the result type-checks.
2. **Turn each production-review bug into a failing test before fixing it** (the table above). Fix the tests that pin buggy behaviour at the same time.
3. **Add failure-injection tests** for launch, evaluation, enumeration and parse, including `ProcessCanceledException` run under `ProgressManager.runProcess`. Assert that the service is idle afterwards.
4. **Isolate global state:**
   - Save and restore every `alloy.native.exe.*` property, and never consult the real `PATH`.
   - Add a shared base `tearDown` that resets `AlloyRunService` and the viewer state and asserts that they are idle.
   - Use a test `PreferencesFactory`.
   - Replace sleeps with event waits.
5. **Use table-driven edge-case tests** for text-shape features: documentation signatures and doc comments, lexer numbers and comments, parser recovery, integer literals (negative, hex, underscore), suppressor comment forms, scope edge cases.
6. **Consolidate the copy-pasted helpers into shared base classes,** and add Kover. Examples:
   - `analyze()` ×5;
   - `problems()` ×6 and `Problem` ×4;
   - viewer `open()`/`panelFor()` ×6;
   - the run `setUp`/`tearDown` ×8;
   - the slow-task launchers ×3;
   - `PIGEONHOLE`/`HEAVY_TRANSLATION` ×2.

# Findings by area

## Core: semantics, settings, editor, psi, lexer, parser, highlighting, top-level

### Overview

**What is tested and how.** There are 32 test classes, about 2,300 lines. Almost all are `BasePlatformTestCase` light fixtures; the lexer uses `LexerTestCase` and the parser `ParsingTestCase` (both golden files). Semantic tests compute the model on a pooled thread inside a read action, then exercise resolution, documentation, usages and rename on the EDT. That matches production, where the EDT only ever sees `cachedModel`. Settings tests inject `AlloySolvers.discover` and `findOnPath`, so they do not depend on the real `PATH`, with the exception noted under High. Two corpus tests run the whole parse-and-annotate pipeline over every bundled `util/*` module and the 192 Practical Alloy models.

**Overall quality.** Good. Tests are named after behaviours and spec scenarios, most assertions are exact (`single()`, exact strings, exact offsets), and there are negative tests for many positives: binders out of scope, private names hidden, library names absent from project scope, unknown qualifier, nothing completed in comments. The weak spots are:
- **Cancellation and threading.** This is the main theme of the production review, and the tests cannot see it at all. Worse, one test hides a real bug.
- **Edge cases.** Most of the bugs the production review found in this area are text-shape edge cases (nested brackets, modifiers, keywords as names, later binders, non-physical files). Every test uses the simple shape.
- **Global state.** System properties set during solver discovery leak between test classes and depend on the developer's `PATH`.

### High

- **A cancellation test fakes the very wrapping that breaks cancellation** — `src/test/kotlin/com/serranofp/alloy/semantics/AlloyModelServiceTest.kt:128-132`
  - `testCancellationIsNotCaught` replaces `parse` with a lambda that throws `ProcessCanceledException` directly.
  - The real `CompUtil.parseEverything_fromFile` wraps every non-`Err` throwable in `ErrorFatal("Unknown exception occurred", ex)`. `AlloyModelService.analyze` (`AlloyModelService.kt:137-140`) then classifies it as `Unavailable` and caches it.
  - So the test passes while the production review's Medium bug ("`ControlFlowException` branch can never run") is live. It will become a real bug the moment the High fix (`checkCanceled` in the reporter) lands, and this test will still be green.
  - Nothing in the suite tests the review's High issue either: an uncancellable parse that holds a read lock. No test runs `model()` under a cancelled indicator.
  - **Suggested tests:**
    1. `parse = { _, _, _ -> throw ErrorFatal("Unknown exception occurred", ProcessCanceledException()) }`, then assert that `ProcessCanceledException` is thrown and that a second `model()` call with the real `parse` returns `Model`, which shows the cancellation was not cached.
    2. A test with the real `CompUtil` and a generated model of a few thousand lines: run `ProgressManager.getInstance().runProcess({ service.model(file) }, EmptyProgressIndicator().apply { cancel() })` on a pooled thread and assert `ProcessCanceledException` within a timeout. It fails today and pins the fix.
    3. Optionally, start the parse, request a write action on the EDT, and assert the write action is not delayed by more than X ms.

- **Solver discovery leaks JVM-wide system properties and depends on the developer's `PATH`** — `src/test/kotlin/com/serranofp/alloy/settings/AlloySolversTest.kt:8-24`, `:46-51`; `src/test/kotlin/com/serranofp/alloy/settings/AlloySettingsTest.kt:65-84`
  - `AlloySolvers.findExecutables` (`AlloySolvers.kt:57-63`) sets `alloy.native.exe.<x>` for every executable of every factory, and only when the property is unset.
  - `AlloySolversTest` saves and clears only `yices` and `plingeling`. So:
    - `testNativeAndFileOnlySolversAreNeverListed` (`findSolvers { anything }`) leaves every other executable property (Electrod, NuSMV, …; the exact list is *plausible*) pointing at a temp `#!/bin/sh` file for the rest of the JVM.
    - `AlloySettingsTest.testChangedAnalyzerOptions` calls `analyzerOptions { setOf("sat4j", "sat4j.light") }`. That reaches `AlloySolvers.factory("sat4j.light")` with the default `::onPath` (`AlloySettings.kt:63`, `AlloySolvers.kt:83-84`), which fills the properties from the **real** `PATH`.
  - As a result, `testWithoutExecutablesOnlySat4j` (`AlloySolversTest.kt:33-36`, which expects exactly the three SAT4J ids) depends on test order and on what is installed on the machine. The global state also leaks into run-layer tests.
  - **Suggestion:**
    - In `setUp`, enumerate `SATFactory.getAllSolvers().flatMap { it.executables }`, then save and clear all of those properties, and restore them in `tearDown`.
    - Make `AlloySettingsTest` pass a `findOnPath` (or inject the factory lookup) instead of hitting `::onPath`.
    - Add an assertion that no test leaves a property pointing into a temp directory.

### Medium

- **Rename to a keyword (or any invalid name) is untested; it throws inside the write action** — `src/test/kotlin/com/serranofp/alloy/semantics/AlloyRenameTest.kt` (whole file)
  - Every rename uses a valid identifier. `AlloyElementFactory.identifier` (`AlloyNamedDeclaration.kt:18-22`) throws `IllegalArgumentException` for `sig`, `run`, `all` and the rest (production review, Medium). There is no `NamesValidator`.
  - Related: `identifier("a b")` parses `sig a b {}` and silently returns the identifier `a`, so a rename to `"a b"` would rename to `a`. This is *plausible*, by reading the factory.
  - **Missing tests:**
    - `myFixture.renameElementAtCaret("sig")`: assert a refusal or validation error and the text unchanged.
    - `LanguageNamesValidation.isIdentifier(AlloyLanguage, "x\"")` is true.
    - `isKeyword("always")` is true.
    - `setName("a b")` is rejected.

- **Documentation tests use only simple bounds, so all four signature-cutting bugs pass** — `src/test/kotlin/com/serranofp/alloy/semantics/AlloyDocumentationTest.kt:57-77`
  - `testFieldSourceWithItsBound` uses `b: set Node`, and all checks are `contains`.
  - The production review's cases are all untested: `f: set (A + B)` (cut at the inner `)`), `pred p[x: A -> B[y, z]]`, `enum E { A, B, C }` (shows `A, B, C`), and `let x = a, y = b | …`.
  - The first name of a group is also untested: by reading `source()`, `a` in `disj a, b: set Node` yields `a, b: set Node`. *Plausible* that this is unintended.
  - Doc comments with modifiers are untested: `/** c */ var f: …`, `private`, `disj`, and the second field of a group.
  - **Suggestion:** a table-driven test over `AlloyDocumentationProvider().source(decl)` and `docComment(decl)` with exact `assertEquals`, on a model with an error so that `source` is used.

- **Documentation shown for a completion item is never tested** — `AlloyDocumentationTest.kt`
  - Nothing calls `generateDoc(lookupDeclaration, leafAtCaret)` where the caret's reference resolves to something else (production review, Medium, *plausible*).
  - **Suggested test:** caret on `foo` in `some fo<caret>o`, with an item `bar` in scope. Assert that `generateDoc(bar, leaf)` contains `bar` and not `foo`'s explanation.

- **Reference resolution in evaluator fragments and non-physical copies is untested** — `src/test/kotlin/com/serranofp/alloy/semantics/AlloyReferenceTest.kt`
  - The annotator and completion guards are tested in `viewer/AlloyEvaluatorFragmentTest.kt:20-35`; the reference paths are not (`AlloyReference.kt:48,60,72`).
  - **Suggested tests:**
    - `PsiFileFactory.createFileFromText("m.als", AlloyLanguage, …)` (virtual file is null): call `multiResolve` on a pooled thread inside a read action, and assert no NPE and a by-name result. The NPE is *plausible* via `collect()` → `AlloyPositions.filename(null)`.
    - In an evaluator fragment: install a counting `parse` and assert it is never called.

- **The binder-scope tests cover only a binder's own bound, not later binders** — `AlloyReferenceTest.kt:135-140`, `AlloyScopesTest.kt:17-22`, `src/test/kotlin/com/serranofp/alloy/editor/AlloyCompletionTest.kt:45-47`
  - All three test `all x: x.f` (own bound, correctly out of scope). None tests `all x: A, y: x.next | …`, where `x` must be in scope in `y`'s bound. Today it resolves by name to something else (production review, Low).
  - **Suggested tests:** in a model with errors, `target("x.next")` is `AlloyBinderDecl`, and completion at `y: <caret>` offers `x`.

- **`AlloyScopes.resolve` and `AlloyScopes.visible` disagree on privacy, and no test covers either side of `resolve`** — `src/test/kotlin/com/serranofp/alloy/semantics/AlloyScopesTest.kt:67-75`
  - `testPrivateDeclarationsOfOtherModulesAreHidden` tests only `visible`.
  - `resolve` (`AlloyReference.kt:132`) has no `isPrivate` filter. So with a model error, navigation, by-name find usages and rename resolve `hidden` to another module's `private pred hidden`, which completion hides. This is a new finding, verified by reading the code.
  - **Suggestion:** either test that behaviour deliberately or filter it. Also add `resolve` tests for `this/A` and for path qualifiers (`util/ordering/first`); today only the alias case is tested (`AlloyReferenceTest.kt:157`).

- **Model-service invalidation and module-graph edge cases are untested** — `AlloyModelServiceTest.kt`
  - Only edits to the file itself and to an opened module are tested.
  - Missing:
    - Creating `lib.als` after `main.als` failed on `open lib` (relies on `VFS_STRUCTURE_MODIFICATIONS`).
    - Deleting or renaming an opened module.
    - An open cycle (`a` opens `b`, `b` opens `a`): `collect` must terminate, and `reaches` must handle cycles.
    - A diamond of opens.
    - Module-name mismatch (`lib.als` declares `module other`).
    - `open` of a non-existent module.
    - Two concurrent `model()` calls: count `parse` invocations. This documents the review's double-parse finding (*plausible*).
    - `openedPath` returning null, and `up` climbing past the root (`openedPath("/main.als", "a/b/main", "x")`).
  - The spec scenario "Analyzer failure → navigation still works by name" (`openspec/specs/alloy-semantics/spec.md:198`) is only half tested. `testAnalyzerExceptionIsUnavailable` does not check that a reference then resolves by name.

- **Annotator branches beyond the happy paths are untested** — `src/test/kotlin/com/serranofp/alloy/semantics/AlloyExternalAnnotatorTest.kt`
  - Every error is a type error. Missing:
    - A **syntax** error from the analyzer, for example `sig A {` at end of file, which exercises `clamp` and a `Pos` past the end.
    - The file-level fallback when no `open` leads to the error, including errors inside library modules (production review, Low: reported for the whole file instead of at the `open`).
    - Two `open`s leading to the same broken module, which should give two annotations.
    - A warning inside an opened module, which must *not* show in the opener.
    - `Unavailable`, which must give no annotation and no IDE error.

- **Settings with out-of-range or null persisted values are untested** — `src/test/kotlin/com/serranofp/alloy/settings/AlloySettingsConfigurableTest.kt`, `src/test/kotlin/com/serranofp/alloy/settings/AlloySettingsTest.kt`
  - `reset()` with `coreMinimization = 7` throws (production review, Low).
  - `skolemDepth = 9` is silently not selectable, so the page would stay modified (*plausible*).
  - `state.solver = null` leads to `addItem(null)`.
  - The `coerceIn` clamping in `analyzerOptions` has no test at all.
  - **Suggested tests:** load an `AlloySettingsState` with those values through `loadState` (as a hand-edited `alloy.xml` would), then assert `configurable(...)` does not throw and `analyzerOptions` clamps.

## `run`, `run/tests` and `analysis`

### Overview

There are 19 test classes, about 2,900 lines. Almost all of them are `BasePlatformTestCase`s that share one light project. The rest are plain `TestCase`s for the pure code: `AlloyRunLogTest`, `AlloyCommandResultTooltipTest` and `AlloyVacuityQueriesTest`.

The suite uses three styles:
1. **Recorded or synthetic events fed straight into the code.** Events go into `AlloyCommandExecution.accept` or `AlloyRunLog.accept`. These tests are deterministic and fast.
2. **Real end-to-end analyses.** These run on the bundled SAT4J (`service.launch` + `waitUntilIdle`, or `AlloyCommandTask.run` on a pooled thread).
3. **Long-running analyses held open on purpose.** `PIGEONHOLE` with `symmetry = 0`, `HEAVY_TRANSLATION`, and a `CountDownLatch` that gates the vacuity follow-up keep an analysis "in flight" so stop and cancel paths can be exercised.

Overall quality is good:
- The assertions are mostly exact: full log lines, tooltip HTML, service-message names and order.
- Stop, cancel and vacuity-handover paths are exercised with real threads.
- The SM runner is tested through its actual TeamCity output.

The main weaknesses:
- Almost every High/Medium bug from `vibe/review/2026-10-22-main.md` in this area is **uncaught**.
- Several tests **encode the buggy behaviour as the spec**: label-only lookup, a hint that cannot be clicked during the vacuity check, and a mouse listener that accepts any end-of-line inlay.
- Exception injection is missing on the launch path, and the cancel tests run the task outside `ProgressManager`.
- A few tests depend on timing.

## `simplifications`, `inspections` and the Practical Alloy corpus tests

### Overview

**How it tests.** Most tests are fixture tests (`BasePlatformTestCase`). They configure a small model, run `doHighlighting()`, and assert the exact `(text, message)` pairs reported, or the exact text after a quick-fix or intention. Shared harnesses:
- `AlloySimplificationTestCase` provides `fixed`, `fix` and `assertNotReported`.
- `AlloyIntentionTestCase` provides `invoked` and `assertNotOffered`.
- `AlloyRewriteTestSupport` runs rules on the model off the EDT.

**Stronger oracles.**
- `AlloyRewriteEquivalenceTest` asks the analyzer (sat4j, 4 steps) whether a formula and its rewrite agree.
- `AlloyRewriteRenderTest` re-parses the output and compares ASTs against an explicitly parenthesized form.
- `AlloyCommandBoundsTest` compares the `ScopeComputer` port with the analyzer's `actualScopes` over the book corpus.
- The two `PracticalAlloy*` tests snapshot every problem reported over the book's models. They are a good false-positive net. The simplification one also checks that each fix still type-checks.

**Overall quality.** Good. Assertions are mostly exact rather than `contains`, and most positive tests have a negative counterpart. The weak points:
- The round-trip oracles never put a rewrite in a real context (`;`, method call, `let`).
- "Problem gone after the fix" is checked in a way that also passes when the fix breaks the model.
- The previous review's bugs are almost all untested. Of the 2 High, 4 Medium and about 12 Low bugs it lists in this area, the suite would catch none.

### Positive notes

- Assertions use the analyzer as the oracle (`toString`, `format`, `eval`, `parseOneExpression_fromString` error text, `DarkPalette.ide` selection) rather than copied literals. That makes them strong and keeps them aligned with the Alloy desktop app.
- The fixtures in `ViewerTestSupport.kt` are deterministic ("exactly one trace") and documented, which makes the lasso, self-loop and loop-target tests precise.
- `DarkColorsTest` checks properties (hue kept, lightness band, ordering, WCAG contrast, HSL round trip) over every `DotPalette`×`DotColor` colour. These are excellent pure tests.
- Good regression tests for subtle issues:
  - `testOutdatedNeedsNoReadAccess` (pool thread without read access);
  - `testAtomOfAnotherSolutionIsNotFound` (stale module globals across enumerated solutions);
  - `testDesktopPreferencesAreUntouched`;
  - `testNewForkEvaluatesEveryWatch`, which checks *exactly* which (model, expression) pairs are evaluated.
- The `TestOnly` hooks (`runner.evaluate`, `viewer.fork`) are small and let the concurrency tests use latches instead of sleeps in most places.
- Teardown is careful: enumerations stopped, executions terminated, watches and visibility reset, panels parented to `testRootDisposable`.
